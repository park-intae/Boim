# 📘 프로젝트 기본 규칙 (Global Rules)

> 이 파일은 프로젝트의 프론트엔드 및 백엔드 코드 작성 시 **최우선적으로 적용되는 핵심 지침**을 명시하는 파일입니다.  
> Antigravity 에이전트는 프로젝트 내 모든 활동 및 코드 생성 시 이 파일의 규칙을 가장 먼저 참조하고 엄격하게 준수해야 합니다.

---

## 🎯 컨텍스트

- **프로젝트명:** Boim
- **프로젝트 목표:** 개인 보험 가입 현황 관리 캘린더 및 대시보드 개발
- **프론트엔드:** React 19 (Vite, TypeScript, oxlint)
- **백엔드:** NestJS 11

---

## 🏗️ 아키텍처 및 기술 표준

### 1. 기술 스택 준수
- `frontend` 디렉토리에서는 **React 19 (Vite, TypeScript, oxlint)**를 사용합니다.
- `backend` 디렉토리에서는 **NestJS 11**을 엄격히 사용하며 각 프레임워크의 권장 패턴을 따릅니다.

### 2. 패키지 매니저 & Node 버전 고정
- **패키지 매니저:** 프로젝트 전체에서 하나로 통일(예: `pnpm`)하여 혼용을 방지합니다.
- **Node 버전:** `.nvmrc`를 통해 고정하여 일관된 환경을 유지합니다.

### 3. 타입 공유 및 검증 전략
- **타입 동기화:** FE/BE 간 타입 동기화를 위해 `packages/shared-types` 워크스페이스를 통해 DTO/인터페이스를 공유하거나, 백엔드에서 정의한 스키마(`zod`, `class-validator`)를 프론트엔드에서 추론 가능하도록 구성합니다.
- **런타임 검증:** 런타임 유효성 검사 도구(예: `zod`)를 통해 API 응답 스키마를 꼼꼼히 검증합니다.

### 4. 상태 관리 & 데이터 페칭 전략 (프론트엔드)
- **서버 상태:** 캘린더, 대시보드 데이터 등 서버로부터 가져오는 상태는 **TanStack Query**로 관리합니다.
- **클라이언트 상태:** UI 상태 등 클라이언트 전용 상태는 **Zustand**나 **Context API**를 활용하여 서버 상태와 명확히 분리합니다.

### 5. 디렉토리 및 네이밍 컨벤션 (모듈화)
- **프론트엔드:** 도메인 주도 디렉토리 구조를 구성합니다.
  - `frontend/src/features/{도메인}/components|hooks|api|types` 
  - `frontend/src/shared/` 
- **백엔드:** NestJS 역시 도메인별 모듈 구조(`insurance/`, `calendar/` 등)로 명확히 분리하여 의존성과 결합도를 낮춥니다.

### 6. 공통 API 응답 및 에러 포맷
- 모든 API 응답은 아래의 공통 포맷으로 통일합니다.
  ```typescript
  { 
    success: boolean; 
    data?: T; 
    error?: { 
      code: string; 
      message: string; 
    } 
  }
  ```
- **백엔드:** 글로벌 `Exception Filter`를 적용하여 에러를 포맷팅합니다.
- **프론트엔드:** 공통 `axios`/`fetch` 인터셉터를 두어 일관되게 에러를 핸들링합니다.

## 🤖 에이전트 지침 및 개발 원칙

### 1. 🔒 개인정보 보호 및 보안 (★가장 중요)
- **응답 및 로깅:** 보험사명, 증권번호, 보장금액 등 민감 정보는 API 응답과 로그 노출을 최소화하며, 특히 백엔드 로깅 시 반드시 마스킹 처리합니다.
- **클라이언트 저장소:** 프론트엔드 브라우저 스토리지(`localStorage` 등)에 민감 데이터를 평문으로 저장하는 것을 엄격히 금지합니다.
- **권한 관리:** 다중 사용자 확장을 대비하여 DB 조회 시 Row-level 권한 체크를 수행해 반드시 **본인 데이터만 조회 가능**하도록 구현합니다.
- **환경 변수:** 민감한 정보는 `.env`로 철저히 관리하며 하드코딩하지 않습니다.

### 2. 🗓️ 날짜 및 시간대 처리
- 캘린더/보험 앱의 특성상 날짜 계산 버그는 치명적입니다.
- **Timezone:** KST로 고정하는 등 타임존을 명확히 설정합니다.
- **라이브러리:** `date-fns` 등 신뢰할 수 있는 날짜 포맷 라이브러리를 일관되게 사용합니다.

### 3. 💬 커뮤니케이션
- 항상 한국어로 정중하고 친절하게 답변하며, 기술적 결정 사항을 이해하기 쉽게 설명합니다.

### 4. 📝 체계적인 작업 계획
- 새로운 작업 전 반드시 `.agents/Phase` 폴더에 마크다운 체크리스트 계획을 작성합니다. (파일명은 `Phase01_harness.md`, `Phase02_harness.md`와 같은 네이밍 규칙을 따릅니다.)
- 작업 순서대로 진행하며 완료된 단위 작업은 즉시 업데이트(`- [x]`) 합니다.

### 5. ✨ 코드 품질 및 리팩토링 원칙
- **엄격한 타입 정의 (`any` 절대 지양):** 프론트엔드와 백엔드를 막론하고 `any` 타입 사용을 극도로 지양합니다. 반드시 구체적인 DTO나 제네릭, 인터페이스를 사용하여 완벽한 타입 안정성을 확보하십시오.
- DRY(Don't Repeat Yourself) 및 SOLID 원칙을 고려해 재사용 가능하고 가독성이 높은 클린 코드를 작성합니다.

### 6. 🌿 Git 브랜치 및 커밋 전략
- `Conventional Commits`(`feat:`, `fix:`, `refactor:` 등) 규칙을 준수합니다.
- **Task 단위 커밋:** 하나의 단위 작업(Task)이 끝날 때마다 즉각적으로 커밋(`git commit`)을 수행하여 변경 사항을 안전하게 저장합니다.
- 기능별 브랜치(`feature/`, `fix/`) 전략을 사용하며, PR 전 빌드/린트/테스트 통과 여부를 필수로 체크합니다.

### 7. 🧪 테스트 검증 필수
- **기능 개발 시 테스트 코드 동반 작성:** 새로운 기능이 제작되면 기능의 단위/통합 테스트 코드를 반드시 함께 작성하여 커밋해야 합니다.
- 모든 코드 변경 후에는 해피 패스 및 엣지 케이스 테스트를 실행하여 통과(Pass) 여부를 검증합니다.
- **프론트엔드:** `Vitest` + `React Testing Library` (사용자 인터랙션/렌더링 위주)
- **백엔드:** `Jest` (유닛 테스트, 의존성 모킹) + `Supertest` (E2E)

### 8. 🚀 웹 품질 및 최적화 (Lighthouse)
- 성능, 접근성(Accessibility), Best Practices, 검색엔진 최적화(SEO) 지표를 항상 고려하여 프론트엔드를 개발합니다.

### 9. 🗂️ 영역별 하네스 파일 및 작업 단계별 하네스 절대 준수 (★★★ 극도로 중요, 위반 시 치명적 오류 발생)
- **절대로, 무조건, 무슨 일이 있어도 하네스(Harness) 파일의 지침과 체크리스트에 근거하여 작업하십시오.**
- **경고 1:** 하네스에 명시된 순서와 요구사항을 무시하거나 임의로 판단하여 누락하면 프론트/백엔드 연동 및 시스템 전반에 심각한 에러가 발생합니다.
- **경고 2:** 작업 시작 전 반드시 현재 진행 중인 Phase의 하네스 파일(`.agents/Phase/` 내부)과 영역별 하네스(`FRONTEND_HARNESS.md`, `BACKEND_HARNESS.md`)를 꼼꼼히 읽고 **절대적으로** 따르십시오.
- **경고 3:** 하네스를 잊고 독단적으로 코드를 작성하는 것은 이 프로젝트에서 가장 엄격하게 금지된 행위입니다. 반드시 하네스에 근거하여 작업을 진행하십시오.
